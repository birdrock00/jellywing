# Intent — Delete the playing song from the Jellyfin library (and every playlist holding it)

## Problem / who

The listener (the device owner on a Jellyfin 12.4 fork server). While a song is playing they decide
it should not be in their library at all — a duplicate, a bad-import track, something that slipped
into a playlist. Today jellywing has no way to retire an item: they must stop the music, find the
item in the Jellyfin web UI (or on the NAS), delete it there, and hope the app catches up. The
player's overflow menu has favorite / clear queue / save queue / sleep timer, and nothing that
removes the thing they are hearing.

## Success outcome

While a song is playing, the player's top-right 3-dot overflow offers **"Delete from library"**. The
user confirms, and the song is gone from the Jellyfin library and from every playlist that contained
it — no web UI, no server-side work. Playback does not die: the queue moves on. If the server
refuses, the user is told why and nothing is claimed as deleted.

## Observable behavior

Android UI + one HTTP call — an overflow item in `R.menu.menu_player` opens a confirmation dialog;
on confirm the app issues `DELETE {server}/Items/{songId}` and shows a success toast (item gone,
queue advanced) or a failure toast naming the reason (401 permission / 404 already-gone / network).

## Scope / boundaries

**In scope**
- A `action_delete_from_library` item in the player overflow menu (title string + `showAsAction="never"`),
  reaching both player themes via the shared `AbsPlayerFragment.onMenuItemClick` handler
  (CardPlayerFragment and FlatPlayerFragment both inflate the same menu).
- A destructive-action confirmation dialog before any network call.
- The delete call itself via the existing apiclient (`ApiClient.DeleteItem(id, EmptyResponse)`),
  with distinct user-visible outcomes for success, 401, 404, and transport failure.
- Client-side aftermath: the deleted item leaves the queue per the chosen option below, the
  mini-player/now-playing surface stops pointing at a dead item, and library screens that show it
  (notably Favorites) refresh rather than sit stale.
- Version bump, unit tests, and the destructive-on-device QA the operator has mandated (below).

**Out of scope**
- Any change to the Jellyfin server: source, DB rows, config, images, user permissions. See Constraints.
- Undo/restore in the app — the stock endpoint destroys the file and there is no server trash.
- Bulk/multi-select delete, folder- or library-scoped delete, "remove from this playlist only" as a
  separate feature, delete entry points outside the player (song lists, album views, playlists), and
  deleting anything that is not a playing audio item (albums, artists, playlists themselves — the
  existing playlist-delete path stays as it is).
- Server-side permission provisioning (granting the app user delete rights) is the operator's action
  in the Jellyfin dashboard, not app behavior.

## Chosen options

- **Destructiveness — accepted, hard delete.** `DELETE /Items/{itemId}` deletes the media file from
  the NAS as well as the library row. The operator accepts this and requires the confirm dialog to
  say so plainly (removes from server + playlists, cannot be undone).
- **Menu visibility — option (b) default:** show the item only when a real server-backed song is
  current; hide it when nothing is playing / the current item has no server id. Permission is NOT
  probed client-side; a 401 comes back as a clear toast.
- **Playback after delete — option (b):** remove the deleted entry and auto-advance to the next
  queued track (no dead mini-player, no silent stop).
- **Stale surfaces + i18n — default:** reuse the `FavoritesStore.notifyChanged()` listener pattern so
  the Favorites tab refetches immediately; other library tabs may rely on their existing
  reload-on-visible. New strings in English only; the 37 `values-*` locales fall back.
- **Test item — operator-nominated:** the track **"<redacted fixture track>"** in the playlist **<redacted fixture playlist>**.
  It is designated expendable and for testing only, and the operator requires that it IS in a
  playlist, so playlist cleanup is actually exercised (see Constraints → QA).

## Constraints

- **The Jellyfin server is read-only (hard, operator-stated, applies to every agent on this
  feature).** No change to server source, database rows, configuration, or running images, and no
  patched server builds. Reading server state (GETs, read-only sqlite, request logs) and calling
  stock endpoints from the app is allowed; making the server behave differently is not. This
  restates hard rule §7 of the research handover.
- **Server facts the Architect must design against (verified against local sources, 2026-11-12):**
  - `ApiClient.DeleteItem(String id, EmptyResponse)` exists (`jellyfin-apiclient-java` @
    `ApiClient.java:2056`) → `DELETE {server}/Items/{id}`, using the app's existing auth. The app
    already uses it for playlists (`PlaylistUtil.deletePlaylist`).
  - On the fork (`v12.4`, `LibraryController.cs:362`) the endpoint is plain `[Authorize]`, **not**
    admin-only as the research note claimed. The gate is `item.CanDelete(user)` →
    `IsFileProtocol` plus `IsAuthorizedToDelete`, which needs `PermissionKind.EnableContentDeletion`
    or a folder entry in the `EnableContentDeletionFromFolders` preference (`BaseItem.cs:878`).
    Only the first/admin account gets that permission by default (`UserManager.cs:766`), so the
    app user's delete rights are an operator dashboard setting, not a code problem.
  - **Refusal is `401`, not 403**; missing/hidden item is `404`. The apiclient surfaces the status
    (`VolleyErrorListener` sets `HttpException.getStatusCode()`), so the app can branch on it.
  - The delete **deletes the file on disk** (`DeleteOptions { DeleteFileLocation = true }`).
  - Playlist cleanup is server-side and automatic: `ItemPersistenceService.cs:145-146` deletes
    `LinkedChildren` rows by both ParentId and ChildId, and playlist entries are
    `LinkedChildEntity(ParentId=playlist, ChildId=song)`. So playlist rows referencing a deleted
    song vanish without client work — **but** the research note cited the wrong half of that
    mechanism, and a file-backed `.m3u8` playlist is NOT rewritten by item deletion
    (`PlaylistManager.cs:668` rewrites only on playlist edits). E2E must assert the playlist in the
    app and via the API, not just the DB row.
  - `UserData` rows (favorite flag, play history) are not deleted: they are re-pointed to a
    placeholder item with a retention date (`ItemPersistenceService.cs:128`). Consequence the
    Architect should reflect in copy/expectations: after a restore-and-rescan the file comes back
    with a **new item id, no favorite flag, and no play history**; the playlist entry does not come
    back at all.
- **QA is a first-class deliverable of this feature (operator-mandated).** End-to-end on the real
  phone against the real server, not unit tests alone: back up the exact test file somewhere outside
  the library **before** each deletion, delete via the app, assert the outcome (server + app), then
  **re-add the file to the library and re-add it to the <redacted fixture playlist> playlist — after every
  deletion, each time it is tested**, so the feature is exercised repeatedly against the same
  nominated track and the library is left as found. The track is for testing only. Never delete any
  other item; never touch items that are operator favorites. `/Library/Refresh` requires elevated
  rights, so the restore-then-rescan path may need the operator to trigger a scan — treat that as a
  known dependency, not a licence to skip the restore. Rebooting the device is forbidden in QA runs.
- Client-only, no new HTTP plumbing, follow existing patterns in the repo (dialog in
  `dialogs/`, toast helper in `MusicUtil`, `MusicPlayerRemote` queue ops `removeFromQueue(position)`
  / `clearQueue()`, `App.getApiClient()`, `AuthHeaderFix`/`PlaybackAuthHeaders` for headers).
  `MusicPlayerRemote` has no remove-current-and-continue primitive — the Architect must decide the
  queue mechanics rather than assume one exists.
- GPLv3 license and F-Droid buildability stay intact; no PII, server credentials, tokens, device
  identifiers, or local paths in committed source, tests, or GitHub artifacts.
- Stage: production — `specs/product.md` frontmatter (`stage: production`). Note that product.md is
  still the seeded TODO template; reconcile if that changes first.
- `workflow.require_spec_approval: true` — this feature stops at `spec-ready` for human approval.

## Open questions

1. Does the current `Song` model carry what is needed to know the item is a real server-backed item
   with a deletable id (vs. a locally cached copy or an empty queue)? Where is the cleanest gate for
   visibility option (b)?
2. Local cache interplay: if the deleted song was cached/downloaded (`database/Cache`,
   `DownloadService`), should the app purge the cache row and cached file too, or is leaving them an
   acceptable orphan the Architect explicitly accepts?
3. Queue mechanics for option (b): removing the *current* index and continuing is not a primitive —
   is it `removeFromQueue(position)` + advance, a re-open of the trimmed queue at the same position,
   or stop-then-play-next? What happens to shuffle order, sleep timer, and the media-session
   notification?
4. Interaction with the favorite-fix suppression guard (`favorites_guard` /
   `sSuppressServerReportsForItemId` from the v1.3.13 work): if the item being deleted is the one
   under report suppression, must the guard be cleared so a stale guard cannot linger against a dead
   id across restarts?
5. Does the app need to stop playback/session before the DELETE to avoid the server or the
   websocket tripping over a session whose now-playing item disappears mid-report?
6. Error copy: is a single toast per failure class enough, or should 401 name the fix (ask the
   server admin / enable media deletion for this user) — and should the confirm dialog list the
   playlists that will lose the entry (that needs an extra query; cost vs. value is the Architect's
   call)?
7. `verification.test_command` in `harness.config.yaml` is empty ("set during bootstrap") and
   `E00-F01` (harness bootstrap) is still `pending`. The Reviewer's verification gate needs a real
   command — confirm with the Orchestrator whether `./gradlew compileDebugJavaWithJavac
   testDebugUnitTest` is adopted as the gate for this feature or whether E00-F01 lands first.
8. Should the new menu item be hidden for the duration of an in-flight delete (double-tap = second
   DELETE on a dead id), and is a 404 on the retry surfaced as success ("already gone") or as an
   error?
