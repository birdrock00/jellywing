- [2026-11-12 builder] AGP connectedDebugAndroidTest on this host uninstalled app+test APKs (deletePackageX) after the run and wiped the app login, then retried against the wiped app — iterate instrumented tests with `adb install -r -d` + `am instrument -w -e class`, and treat any gradle connected run as a session-destroying event.
- [2026-11-12 builder] Never read or dump the operator's credential/session cache (kept outside the repo) even to debug: the values land in the run log; the builder lane needs zero credentials — device E2E is QA's protocol.
- [2026-11-12 reviewer] Before accepting a "deferred to QA" test row, grep for the named method: E01-F01's `.tests.md` mapped R3/R4/R9/R10 to five `e2e*` methods that were never written (only `e2e4_cancelNoop` exists), so a deferral can silently read as coverage — a deferred row must say NOT YET WRITTEN, and a source-contract test that asserts whole-file `contains(...)` cannot tell which branch ran, so scope it to the branch.
- [2026-11-12 reviewer] `am instrument` prints `OK (N tests)` and logcat prints `run finished: N tests, 0 failed, 0 ignored` even when every leg died in `assumeTrue` — on E01-F01 three of four instrumented legs skipped silently (no app session; `e2e4` needs driver args from a driver that was never written). Per-test `started:`/`finished:` lines are the only executed-proof; treat `assumption failed` as NOT RUN.
- [2026-11-12 reviewer] A mutation a Builder reports as KILLED must be re-run with only the named contract test in the run: E01-F01's optimistic-success mutant was red because dispatching SUCCESS crashes on a JVM with no bound service, not because the assertion fired. Isolation (`--tests Class.method`) is what separates a kill from a crash.
- [2026-11-12 reviewer] Fixing a multi-item mutation loop is half-pinned unless the *iteration order* is exercised: E01-F01's every-queue-entry fix asserted `contains("removeFromQueue(positions.get(")`, which an ascending loop (provably leaving a dead entry, since the bounds guard silently refuses the stale index) satisfies verbatim. Extract the order into a pure helper and test it.
- [2026-11-12 reviewer] A device fixture whose path is derived from metadata instead of the run-unique id poisons the suite after one failing run (E01-F01 `CachePurgeOnDeleteInstrumentedTest`: the later run fails "fixture file must be creatable" rather than the requirement) — fixtures must delete their own stale files before creating them.
- [2026-11-12 builder] Parse JUnit XML with a real parser, never a regex, when pairing test-name ↔ failure-message: `<testcase …/>` self-closes on success, so a non-greedy regex attributes every kill to the preceding (unrelated) test name and the run report names the wrong killer (E01-F01 r3).
- [2026-11-12 builder] Never type `git checkout --` without a pathspec, even "just to see status": it is a no-op only by accident of tree state, and it is the one revert path the harness forbids. Take `cp` backups before the first mutant and restore per-file (E01-F01 r3, disclosed).
- [2026-11-13 orchestrator] Size a Builder brief by the child's OUTPUT budget, not by the work: E01-F01 round 5 died at stopReason=length on turn 29 with zero commits because one brief asked for five complex E2E methods plus three driver fixes and left all context-gathering to the child (its fourth such death). - [2026-11-13 builder] An oracle whose trigger lives in a LATER driver phase must not poll inside the blocking `am instrument -w` call that precedes it: in delegated mode e2e2 waited 180 s for a `/Library/Refresh` the driver only POSTs after the run returns — a guaranteed false red paid for with a real destructive delete. Assert in-test only what is observable before the call returns, print a `PARTIAL (… delegated to driver …)` declaration, and let the later driver phase carry the rest (never a backgrounded racing scanner: that trades the false red for a false green) (E01-F01 r6/F1).
- [2026-11-13 orchestrator] Diagnose with turn-level timing, never with the harness's own telemetry: E01-F01's `telemetry.jsonl` has a null `duration_s` on 62% of rows, and a "62% was coordination overhead" claim read straight off it was an artifact of missing data. Timing assistant turns from the run transcripts showed ~64% of a 14.3 h day was raw model generation at ~19 tok/s on one local Q4 GGUF, with a 20:1 thinking-to-visible-text ratio. The first lever was the model, not the process — and the product code was finished after 4 of those 14 hours (`better-agentic-system.md`).
- [2026-11-13 orchestrator] A shipping gate that needs a device and a credential is a test-pyramid gap, not a review gap: this repo had 150 JVM tests, zero Robolectric and no `managedDevices`, so every UI assertion had to become an instrumented test and every real-server state became a human-gated destructive cycle. Six review rounds could not close C-B because no amount of reviewing opens a gate only a device can open. Fix the pyramid before adding rounds.
- [2026-11-13 builder] A helper whose failure path is `die()` must be CALLED BARE, never in `$(…)`: `die()` prints its `PHASE … FAIL` line and the final report to **stdout**, so command substitution captures — i.e. swallows — exactly the failure output, and the outer shell sails on with the message in a variable. Design hardened helpers that echo a value for interface reasons to be invoked bare with the value treated as log data (or route the count via a nameref), and say so in the helper header (E01-F01 C-1, found while designing playlist_items_checked).
- CORRECTION to an earlier lesson: it said per-test `started:`/`finished:` lines are the only executed-proof. Those lines do not appear in `am instrument -w` JUnit-formatted output at all. Measured 2026-11-13: a class-level run containing an assume-skipped test prints `OK (2 tests)` — **skips are counted as passes in the class summary** — and even prints zero dots while claiming two tests. Invoking a single method by name is the discriminator: assumption-failed gives `OK (0 tests)`, real execution gives `OK (1 test)` with Time > 0. So run one method per invocation and accept only `^OK \(1 test\)$`; treat `OK (0 tests)` as NOT RUN. This is why tools/verify-instrumented.sh loops over methods instead of passing a class list, at a cost of ~2.5 min for 18 tests.
- A fail-open gate must log every path, because fail-open and never-ran are indistinguishable from outside. The shipped verify gate did nothing for an entire session: it called `ctx.notify(...)`, a method that does not exist on the pi extension context (it is `ctx.ui.notify(message, level)`, and `ctx` has no `notify`). The TypeError was caught by the handler's own fail-open block, which called `ctx.notify` again and threw a second time, so pi reported a handler error and continued. Nothing appeared to be wrong. Two rules follow: (1) never let an error path depend on the same API that just failed, and (2) prove a hook fires by an artefact it must write (a log line at load), not by absence of complaints.
- A required-parameter change is cheaper than a footgun default. `log(msg, cwd = loadCwd)` silently routed verdict lines into whichever repo the process started in; making cwd the required first argument removed the whole class and immediately exposed the bug in tests.
- Prove the wall before climbing over it. On a server that would not accept admin creation, the decisive datum was the 404 ProblemDetails body and the log line 'No users, creating one with username root' — both of which I had been discarding by sending output to /dev/null across six attempts. Reading one response body beats a tenth verb permutation: I burned several probes cycling POST/PUT/PATCH/content-types when the answer was in the body and in the container log.
- 2026-11-14T00:34:20Z Evidence rule for instrumented runners: "OK (N tests)" from `am instrument` is NOT proof of execution, at any granularity. An assumption violated in @Before or in an @Rule (Espresso/ActivityScenario/GrantPermission rules qualify) is reported as skipped yet counted in the OK total, so a per-method "OK (1 test)" can mean the body never ran — proven by planting a guaranteed AssertionError in a test body and still getting OK (1 test) in 0.075s. The only control that distinguishes the cases is a deliberately misspelled method name (yields OK (0 tests)), which proves the method was found and still not run. A device tier must therefore require a positive marker emitted by the test itself and observed outside the runner output; timing heuristics are not enough because legitimate Room tests run in ~0.03s. Generalise: before trusting any gate, plant a defect that must make it fail; if the gate stays green, the gate is the defect.
- 2026-11-14T01:32:23Z Standing rule for automated credential use: when SSH refuses because the remote host key changed, that is a stop, not an obstacle. Never reach for StrictHostKeyChecking=no, UserKnownHostsFile=/dev/null or -o LogLevel=ERROR to get through, no matter how sanctioned the credential is or how loud the instruction to finish; a valid secret delivered to an impostor is worse than an unfinished task. Report the offending known_hosts line and the presented fingerprint instead, and note that key exchange failed before authentication so nothing was transmitted.
- 2026-11-14T03:32:22Z Three traps that made a shell QA driver report failure without any product being touched: (a) 'local a=$1 b=$a' fails under set -u because bash creates all names in a local statement before assigning any of them — split the declaration; (b) 'adb shell <cmd> "${args[@]}"' hands a space-joined string to the DEVICE shell, which re-parses it, so characters like '#' (as in 'Class#method' for am instrument) become shell syntax and truncate the command — build one quoted command string for the device instead of forwarding an argv array; (c) am instrument silently lacks a target unless '<test-pkg>/<runner>' is passed, and its error names the preceding argument, not the missing one. Generalise: an assertion that never ran and a command that never executed both look identical to a failing test from the outside, so a driver's own plumbing needs the same grip-proof as the product.
